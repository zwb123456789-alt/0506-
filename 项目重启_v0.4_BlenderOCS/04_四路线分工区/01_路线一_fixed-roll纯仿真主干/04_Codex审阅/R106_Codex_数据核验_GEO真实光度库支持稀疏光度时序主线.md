### 1.2 GEO 数据库说明

`01_GEO真实光度数据库信息整合_供回看确认.md` 一句话定性：

```text
有光度、有几何、有型号、有时间序列，但没有目标三轴姿态真值。
因此它是保真度校准级数据，不是监督反演级数据。
```

数据库关键事实：

```text
设备：12 台 15cm 口径相机组成的计算光学阵列。
覆盖：东经 60°~175° 同步带。
成像：FITS，16 bit，4K。
帧率：1 帧/分钟/台。
采集图像：221005 帧，有效图像 214005 帧。
光度范围：-0.382 到 16.784 视星等。
```

最关键的字段能力：

```text
PRE 表：
  有成像时间、目标编号、J2000 坐标、传感器相对目标几何。
  可反算每帧 sun/view 相对几何。

DET/IPD 表：
  有成像时间、目标流水号、测角、赤经赤纬、IPD 测光光度。
  IPD 测光光度 = 真实光度数据本体。

REG 表：
  有 NORAD/CODE，可定位卫星型号，落实“型号已知”。

MAN 表：
  有光度均值/方差/最小值/最大值，支撑工程中的光度异常/机动检测。
```

### 7.8 “评价口径”在本项目中是什么意思

作者追问：

```text
一直在谈评价口径太严苛，评价口径是什么？
```

定义：

```text
评价口径 = 模型训练/推理后，如何把预测结果判定为“对/错/好/坏”的指标规则。
```

它不是数据本身，也不是模型结构，而是评估标准。例如同一个预测结果，可以被不同评价口径给出完全不同的解释。

#### A. 旧的严苛口径：exact-bin

当前 v0.4 早期主指标是 exact-bin classification：

```text
yaw 被离散成 72 个 bin：
  0°, 5°, 10°, ..., 355°。

pitch 被离散成 37 个 bin：
  -90°, -85°, ..., 90°。

模型输出每个 bin 的分类 logits。
预测时取 argmax。
只有 predicted_bin == true_bin 才算对。
```

举例：

```text
true yaw = 100°
pred yaw = 105°

exact-bin 口径：
  错。

原因：
  预测差了 1 个 bin，即 5°，但不是完全相同 bin。
```

再举例：

```text
true yaw = 355°
pred yaw = 0°

普通线性差值会觉得差 355°；
circular yaw 实际只差 5°。

如果 exact-bin：
  仍然错。
```

因此 exact-bin 是非常硬的成功定义：

```text
只奖励精确命中 5° bin；
5° 近邻、10° 近邻、同一粗方向、环绕边界近邻，都算错。
```

#### B. 为什么说它“太严苛”

因为姿态估计更自然的评价通常不是“是否命中同一个离散 bin”，而是“角度误差有多大”。

在本项目里，以下预测都被 exact-bin 算错：

```text
差 5°
差 10°
差 15°
差 30° 但仍在同一粗方向
0°/355° 环绕边界近邻
```

但从物理或工程角度看，它们不是同一种失败。

```text
差 5°：近命中。
差 30°：粗方向可能仍有信息。
差 180°：基本是严重混淆。
```

exact-bin 把这些全部压成一个字：

```text
wrong
```

这就是“评价口径太严苛”的含义。

#### C. R82/E45B 后采用的更合理口径

后续重构的评价口径包括：

```text
1. yaw circular MAE
   环形 yaw 平均绝对误差。
   例如 355° 和 0° 差 5°，不是 355°。

2. within-k
   预测是否落在 k 个 bin 内。
   within-1 = 5° 内；
   within-2 = 10° 内；
   within-6 = 30° 内。

3. coarse-bin
   把 yaw 合并成更粗方向，比如 45° 或 90° 区间，看粗方向是否正确。

4. random/chance baseline
   与随机预测比较，判断是否真的高于 chance。

5. yaw-block stratification
   按 holdout yaw block 分层，看哪些弧段局部可用，哪些弧段完全失败。
```

这些口径不会把所有错误混成一类，而是区分：

```text
近命中；
粗方向正确；
局部 block 可用；
整体外推失败；
接近随机；
严重坍缩。
```

#### D. 评价口径 vs 训练判据

必须区分两个概念：

```text
评价口径：
  训练完之后如何打分。

训练判据 / loss / output head：
  训练时让模型学什么。
```

旧模型的问题可能有两层：

```text
1. 评价口径太硬：
   exact-bin 0% 看起来很惨，但 circular/coarse 指标可能显示仍有弱信号。
   这一点已经通过 P0/P1-A 确认。

2. 训练判据也可能太硬：
   如果训练时就是 72-bin 分类，模型可能没有学到连续角度结构。
   这一点尚未确认，需要 B6/T1 用 continuous/circular regression 实测。
```

最短说法：

```text
评价口径 = 怎么判分。
训练判据 = 怎么训练。
当前已经确认“怎么判分”太苛刻；
还没确认“怎么训练”是否也是失败主因。
```

### 7.9 从 R106 起的任务下达方式：长程任务，不再碎片化

作者要求：

```text
从 R106 开始，每次下达任务不要一个个小任务下达，
而是给 Claude 下达一整个长程任务，必须能看到结果，最后交给 Codex 审阅。
之前一直卡在叙事，始终无法往前推进，效率太低。
```

Codex 接收该要求，并作为 R106 后任务规则：

```text
后续任务单不得只要求 Claude 写“方案/盘点/叙事/候选路线”。
除非任务本身明确是审阅或裁决，否则应下达可执行的长程任务：
  读取上下文 -> 定位代码/数据 -> 实施或生成产物 -> 运行 smoke/正式实验 -> 汇总结果 -> 形成执行报告。
```

#### A. 长程任务的最低要求

每个给 Claude 的任务单必须包含：

```text
1. 明确目标：
   要解决什么技术问题，而不是只整理什么材料。

2. 明确允许范围：
   可读哪些文件；
   可改哪些副本脚本；
   可写哪个结果目录；
   是否允许训练、forward、渲染、新数据。

3. 明确红线：
   哪些旧结果链不得覆盖；
   哪些 claim 不得写；
   哪些成果区/论文正文不得动。

4. 明确必须产物：
   脚本、配置、命令、日志、CSV/JSON/NPZ、图表、结果表、执行报告。

5. 明确验收指标：
   smoke 是否通过；
   是否有正式结果；
   若失败，是否有可复现错误命令和阻塞说明。

6. 明确 Codex 审阅入口：
   Claude 交完整包后，再由 Codex 一次性审阅通过/不通过/FIX。
```

#### B. 禁止继续出现的低效任务形态

后续应避免：

```text
只让 Claude 再写一份路线建议；
只让 Claude 盘点还缺什么；
只让 Claude 解释为什么暂缓；
只让 Claude 生成合并裁决准备；
只让 Claude 输出没有脚本、没有结果、没有阻塞日志的叙事报告。
```

如果确实需要阶段门，也必须写成：

```text
阶段门 + 可执行实施 + 可验收结果
```

而不是单独一个“阶段门叙事文件”。
