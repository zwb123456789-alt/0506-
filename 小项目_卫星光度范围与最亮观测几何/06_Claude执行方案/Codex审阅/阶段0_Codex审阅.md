## 主要问题

### 1. OCS 定义写得过早、过确定

原文写：

```text
E_obs / E_sun = OCS / R^2
```

并称“本项目模块 A 计算的物理量。其定义为……”

问题：

这是阶段1要审计的核心内容，目前不能在阶段0直接写成已确认定义。现阶段更稳的写法是：

```text
候选换算关系之一为 E_obs / E_sun = OCS / R^2；
但当前项目中的 OCS 是否满足该定义，需要在阶段1审计 ocs_core.py、BRDF归一化和单位后确认。
```

原因：

- 可能存在 `4π`、`π`、BRDF归一化、方向性散射量或标定常数；
- OCS 可能是相对量，而不是可直接进入绝对辐照度公式的物理量；
- 当前代码没有轨道距离和波段响应。

### 2. 视星等公式也不应写成确定公式

原文写：

```text
m = m_sun - 2.5 log10(OCS / R^2)
```

问题：

这个公式现在只能作为候选形式，不能作为阶段0术语定义。建议改成：

```text
若阶段1确认 OCS 满足 E_obs/E_sun = OCS/R^2，则可考虑使用
m = m_sun - 2.5 log10(OCS/R^2)。
若 OCS 定义不同，则可能需要 4π、π、波段响应或 K_cal 标定常数。
```

阶段0中唯一可以安全保留为“当前可用”的公式是：

```text
Delta m = -2.5 log10(OCS_2 / OCS_1)
```

前提是两个 OCS 来自同一代码、同一BRDF、同一单位口径。

### 3. “光度（Luminosity / Brightness）”术语建议收窄

原文把光度写成“卫星反射太阳光后在观测者处产生的辐照度或通量”，标题中用了 `Luminosity / Brightness`。

建议：

- 少用 `Luminosity`，因为 luminosity 通常指源的总发光功率；
- 本项目更适合写 `observed irradiance/flux`、`apparent brightness` 或中文“观测辐照度/观测通量/视亮度”；
- 真实星等对应的是观测通量或辐照度比，而不是目标自身 luminosity。

### 4. “OCS 越大观测越亮”禁用表述过强

原文在“不可以说”中写：

```text
"OCS 越大观测越亮" | 未标定；OCS 可能只是相对量
```

建议改得更精确：

```text
不能说“OCS越大就能直接给出真实观测星等”。
但在同一几何、同一BRDF、同一距离/波段口径下，OCS越大可作为相对更亮的判据。
```

否则会和文档中“相对亮度排序可以说”产生轻微冲突。

### 5. phase24/45/63/90/120 的几何标签需避免未核验

原文写：

```text
config 中的 OBS_GEOMETRIES 定义了五组相位角
```

如果阶段0没有直接核验配置文件，建议改成：

```text
项目已有多观测几何结果使用 phase24/45/63/90/120 等标签；具体太阳/观测向量与相位角应以各目录 config_used.json 或 ocs_scan.json 为准。
```

这样更安全。
