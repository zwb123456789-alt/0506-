# 现场口头补充稿（3-5分钟）

> 用途：如果现场已经按原材料讲完项目，可用这段补充说明 v0.4 最新变化。  
> 不需要逐字照读，重点是把“为什么重启”和“想请梁华判断什么”讲清楚。

---

梁总，我这里还想补充一个最新变化。前面讲的结果主要是前期阶段性结果，但最近我对数据源和前向模型一致性做了一轮审计，发现 OCS 和图像之间有一个比较底层的口径问题。

旧版本里，OCS 主要来自模块 A 的 face-level 或 face-center 采样；图像端则来自 Blender 渲染链路。这样虽然都服务于同一个姿态反演任务，但二者并不是完全同源的像素级前向模型。这个问题会影响后面对 OCS-only、image-only 和 fusion 的解释，因为性能差异可能部分来自两套仿真链路差异，而不只是观测模态的信息差异。

所以我现在把 v0.3 暂停作为可投稿版本，进入 v0.4 BlenderOCS 重启。v0.4 的核心不是简单换一个 OCS 文件，而是把 OCS 和图像统一到同一个前向物理模型里：Blender 只负责几何可见性、depth、normal、part ID 和像素级采样；BRDF、太阳入射、OCS 积分和图像线性响应仍由 Python 显式公式计算。这样 OCS 可以理解成同一线性光度响应的积分读出，图像是空间分布读出。

目前 v0.4 还没有新主结果，只完成了方法冻结、manifest 规范和全链路重跑计划。下一步我不打算直接全量重跑，而是先做单姿态 smoke test、depth round-trip、sun-view depth、太阳侧可见性重投影和 20 姿态 shadow validation。只有这些门控验证通过后，再生成完整数据集并重跑 OCS-only、image-only、fusion 和退化实验。

这部分想特别请您帮我判断三点：

第一，从真实光学观测和姿态反演角度看，用 Blender pixel-level geometry pass 生成 canonical OCS，再用显式 BRDF 公式积分，是否比原来的 face-center OCS 更合理？

第二，把 OCS 和图像写成同一前向模型下的积分读出和空间分布读出，这个论文叙事是否成立？

第三，如果 v0.4 重跑后某些指标不如旧结果，我能否把它解释为更严格物理定义下的更可信结果，而不是简单追求数值更好？
