## 近期方法审计与下一步工作更新

在原有 OCS-光度图像仿真与姿态反演工作基础上，我近期对项目的数据源和前向模型一致性做了一轮审计。审计后发现，前期 OCS 数据与图像数据虽然都服务于同一姿态反演任务，但 OCS 端主要来自模块 A 的 face-level / face-center 采样，而图像端来自 Blender 渲染链路。二者在像素级可见性、采样口径和太阳侧遮挡定义上并未完全统一。

这个问题会影响论文的核心解释：如果 OCS 与图像不是同一前向物理模型下的两种读出，那么 OCS-only、image-only 和 fusion 的差异可能部分来自仿真链路差异，而不仅仅来自观测模态的信息差异。

因此，我目前将项目推进到 v0.4 BlenderOCS 重启阶段。v0.4 的核心目标是重建统一前向物理模型：Blender 负责像素级几何可见性、depth、normal、part ID 和世界坐标；Python 公式负责 GGX/Cook-Torrance BRDF、太阳侧可见性、OCS 积分和图像线性响应。OCS 被定义为同一 clean image linear response 的积分读出，图像则是其空间分布读出。

这意味着 v0.3 的旧结果会作为阶段性探索和诊断材料保留，但不再作为最终投稿主结果。后续所有 OCS-only、image-only、fusion、退化鲁棒和补充实验，都需要基于新的 Blender-derived OCS manifest 和统一 image manifest 重跑。

目前 v0.4 已完成方法冻结、数据与 manifest 字段规范、全链路重跑任务清单和代码实施前准备文档。当前还没有新主结果，下一步会先做代码层面的最小验证，包括单姿态 smoke test、depth round-trip sanity check、sun-view depth pass、太阳侧可见性重投影和 20 姿态 shadow validation。只有这些门控验证通过后，才进入全量数据生成和模型训练。

这次想特别请梁华专家帮忙判断：这种用 Blender pixel-level geometry pass 统一 OCS 与图像前向定义的路线是否合理；从真实光学观测角度看，pixel-level OCS、太阳侧可见性、自遮挡和相位角处理哪些地方最需要注意；以及这类“方法审计后重跑”的论文叙事是否更容易被审稿人接受。
